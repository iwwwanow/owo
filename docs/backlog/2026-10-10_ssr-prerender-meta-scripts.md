# Пререндер `.meta/index.js` на сервере → библиотека shared-скриптов

Идея: часть того, что делают JS-скрипты инстанса (`.meta/index.js` и импорты), — статичные мутации DOM: переставить элементы, добавить css-класс, проставить inline-стиль. Их можно выполнять на сервере один раз, отдавать готовый HTML и убрать FOUC/прыжок вёрстки после `DOMContentLoaded`. Конечная цель — библиотека shared-скриптов, через которую пользователь кастомизирует свою страницу, поэтому формат один: **всё на JS, два типа скриптов — `client` и `server` (prerender)**.

## Что куда в текущих скриптах (`test/uploads/.meta/`)

- **Статичные мутации** — хак xtc-toaster в `common.script.js` (`picture.style.width`). → `server`.
- **Качество картинок по размеру карточки** — `common.script.js` читает `getBoundingClientRect()` и переписывает `srcset`. Логически это задача сервера: картинки должны быть нарезаны и закэшированы заранее, а не на первом запросе (сейчас ресайз ленивый, `GetResizedImagePath` с семафором на 3; клиентский скрипт ещё и тянет картинку повторно после загрузки). Но геометрия грида у каждого инстанса своя (CSS инстанса), так что «вычислить ширину из класса» не выйдет — ширину надо **измерять**, то есть нужен настоящий layout-движок.
- **Интерактив** — `frames.script.js` (hover/touch, fetch, таймеры). → `client`.

## Рантайм: headless-браузер и снапшот

Раз грид у инстансов разный, DOM-шимы без layout (goja + свой шим, linkedom/happy-dom) отпадают — они не умеют `getBoundingClientRect`. Остаётся headless Chromium: открыть страницу, дождаться server-скриптов, сохранить `outerHTML` как статику и отдавать её. Плюс — исполняется произвольный пользовательский JS как есть, без ограничений на API.

Чем управлять браузером:
- **`Bun.WebView`** (экспериментальный, bun 1.3.x) — встроенный headless API: `navigate`, `evaluate`, `screenshot`. На Linux сам браузер не встроен — он гоняет установленный Chrome/Chromium по CDP. То есть Chromium в образе нужен в любом случае, Bun просто заменяет Puppeteer.
- **rod / chromedp из Go** — тот же Chromium через тот же CDP, но без второго рантайма рядом с owo. Скриптам всё равно, кто дёргает браузер.

## Подводные камни снапшота

- **Один снапшот = один viewport.** Классы и перестановки от ширины не зависят — их снапшот фиксирует корректно. А измеренная ширина карточки — только для того viewport'а, в котором делали снапшот; мобилка получит десктопные размеры. Решение для картинок: прогнать страницу на нескольких ширинах (например 360/768/1280/1920), собрать ширину каждой карточки на каждой, и записать в HTML `srcset` с `w`-дескрипторами + `sizes` с media-условиями. Браузер сам выберет нужный размер, а все размеры заранее прогреваются в кэш. Т.е. headless — не «финальный DOM», а **измеритель**.
- Почему не рендер «на запросе под ширину клиента»: при первом запросе HTML сервер ширину экрана не знает. Client Hints (`Sec-CH-Viewport-Width`, `Sec-CH-DPR`) есть только в Chromium, приходят после `Accept-CH` (или через `Critical-CH` с лишним круговым запросом); Safari/Firefox их не шлют. Плюс задержка Chromium на каждый запрос и поломка при ресайзе/повороте экрана. А если кэшировать по бакету ширины — это тот же прогон по брейкпоинтам, только ленивый. Итог: замеры заранее, одна страница с `srcset` + `sizes`.
- Альтернатива без замеров: `sizes="auto"` + `loading="lazy"` — браузер сам подставляет реальную ширину. Пока поддерживается только в Chromium-браузерах, остальным нужен фоллбэк `sizes`.
- **Двойное исполнение.** В снапшоте мутации уже применены — server-скрипты надо вырезать из итогового HTML, client-скрипты оставить и сделать идемпотентными. Поэтому деление на `client`/`server` нужно и тут.
- **Случайность и время** (рандомная рамка в frames) замерзают в снапшоте — такое только в `client`.
- **Инвалидация**: пересобирать снапшот при изменении uploads/`.meta/` (mtime или inotify), а не на запросе — запуск Chromium на каждый запрос слишком дорог.
- **Ресурсы**: Chromium в Docker-образе — сотни МБ и заметная RAM на Dokku-инстансе; запуск скриптов из uploads в браузере — песочница (без доступа в сеть кроме самого owo).

## Нагрузка и альтернативы Chromium

Порядки (не мерил, проверить на реальном инстансе): `chrome-headless-shell` (урезанная headless-сборка из Chrome for Testing) — ~100–200 МБ на диске, полный chromium с зависимостями — 300–500 МБ; процесс браузера ~100–200 МБ RAM + вкладка 50–150 МБ (картинки на странице — главный потребитель). Время — от сотен мс до пары секунд на страницу×viewport. Важно, что нагрузка эпизодическая: браузер запускается только на пересборку после изменения uploads и закрывается — в простое 0. Как удешевить: одна вкладка и смена viewport вместо новых запусков; блокировать загрузку картинок через перехват запросов (размеры карточек задаёт грид, не картинка — проверить); очередь с конкурентностью 1; можно вынести в отдельный контейнер, который поднимается по требованию.

WebKit не легче: Playwright-сборка WebKit под Linux тянет GTK/GStreamer и весит сопоставимо, WPE WebKit заточен под embedded, но тулинга под Go почти нет; CDP-библиотеки (rod/chromedp) с WebKit не работают, только Playwright/WebDriver. `Bun.WebView` на Linux — тот же Chrome. Firefox headless — та же весовая категория. Лёгкие движки с layout (Servo, Ladybird, Blitz на Stylo+Taffy) — либо незрелые, либо без JS.

Вариант вообще без headless: замерять на клиенте у реальных посетителей (скрипт и так меряет `getBoundingClientRect`) и слать замеры серверу → сервер копит `sizes` и прогревает кэш. Минусы: первый посетитель на каждом брейкпоинте платит, и эндпоинт надо защищать (whitelist размеров, rate limit), иначе это способ забить диск кэшем.

## Открытые вопросы

- Как помечать тип: имя файла (`*.server.js` / `*.client.js`), `export const target = 'server'` или раздельные точки входа `index.server.js` / `index.js`.
- Формат подключения shared-скриптов из библиотеки + их параметров (селектор, классы) в `.meta/` инстанса.
- Нужен ли гибрид — server-часть скрипта отрисовывает разметку, client-часть его же навешивает интерактив (по аналогии с гидрацией).
- Как server-скрипт отдаёт результат замеров на несколько viewport'ов (например, `export function measure()` → сервер склеивает в `sizes`).
