# Клиентский пререндер силами посетителей

> **Статус: открыто, обсуждение не завершено.** Решений здесь нет — это набросок, флоу нужно подробно рассмотреть, он может оказаться лучше headless-варианта. Главный нерешённый вопрос — доверие к патчам от посетителей (см. «Сомнения: консенсус»). Контекст: `docs/backlog/2026-10-10_ssr-prerender-meta-scripts.md`, архитектура — `docs/backlog/2026-10-10_owo-services-architecture-draft.md`.

## Идея

Скрипт, выполненный в браузере одного посетителя, даёт результат, который нужен всем. Первый посетитель (на данную версию страницы и данный диапазон ширины) выполняет клиентские скрипты как обычно, браузер записывает, что они поменяли в DOM, и отправляет это на сервер. Сервер сохраняет результат, и следующие посетители получают уже готовую страницу без повторного выполнения. То есть вычислительная мощность одного клиента амортизируется на всех. Работает как основной режим без headless-сервиса или как фоллбэк, пока воркер ещё не просчитал страницу.

Важно: это не «отправить `getBoundingClientRect`», а **универсальный инструмент пререндера клиентских скриптов** — должен работать для любого скрипта, который меняет DOM.

## Как сделать универсально — запись мутаций

- Перед выполнением server-помеченных скриптов вешается `MutationObserver` на документ; он отмечает узлы, которые изменились (атрибуты, классы, `style`, перемещения и вставки узлов, текст).
- Когда скрипты закончили — по явному сигналу (`owo.ready()` из скрипта) или эвристике (нет мутаций и сетевых запросов N мс) — финальное состояние этих узлов сворачивается в **патч**: список операций над узлами, адресованных стабильными селекторами (id карточек уже детерминированные, плюс путь от ближайшего id).
- Патч уходит на сервер. Go применяет его к своей разметке через `x/net/html` / goquery — JS на сервере не нужен, патч — это декларативные правила, только сгенерированные автоматически записью, а не написанные руками.
- URL-ы ресурсов внутри патча (например, новые `?width=&height=` картинок) сервер видит и прогревает в кэше — частный случай с картинками решается тем же механизмом.

## Формат патча (набросок)

Не журнал мутаций для повторного проигрывания (порядок, промежуточные состояния, идентичность созданных узлов), а **итоговая разница**: `MutationObserver` только собирает множество затронутых узлов, а в конце для них снимается финальное состояние. Адрес узла считается в **исходном** дереве (до скриптов, сохраняется в `WeakMap` на старте): `id` ближайшего предка + индексы element-детей (текстовые узлы не считаются) — Go отдал тот же HTML, так что адрес детерминирован.

```json
{
  "v": 1,
  "page": "/",
  "source": "sha256:<html+scripts>",
  "viewport": "any",
  "ops": [
    { "op": "attr",   "at": { "id": "card-_featured-projects-xtc-toaster", "path": [0] }, "name": "style", "value": "width: calc(100% / 6); flex-shrink: 0;" },
    { "op": "class",  "at": { "id": "grid-frames-script" }, "add": ["grid--wide"], "remove": [] },
    { "op": "move",   "at": { "id": "card-a" }, "to": { "id": "grid-main" }, "index": 0 },
    { "op": "insert", "to": { "id": "grid-main" }, "index": 3, "html": "<div class=\"spacer\"></div>" },
    { "op": "remove", "at": { "id": "card-b" } },
    { "op": "text",   "at": { "id": "title" }, "value": "..." }
  ],
  "resources": ["/cover.png?static&width=380&height=576"]
}
```

Хранение — JSON на ФС рядом с кэшем: `cache/prerender/<page>/<source-hash>/<viewport>.json`, кандидаты от клиентов до консенсуса — `.../candidates/<patch-hash>.json` со счётчиком. Go применяет принятые патчи один раз и кэширует итоговый HTML — на запросе работы нет. Патч, а не готовый HTML-снапшот: меньше, его можно провалидировать по белому списку операций и сравнивать/сливать между диапазонами ширины.

Ограничения `MutationObserver`: не видит изменения CSSOM (`sheet.insertRule`), свойств без атрибутов (`input.value`, `checked`), содержимого canvas, shadow DOM без отдельного наблюдения. Такие скрипты — только `client`.

## Зависимость от ширины экрана

- Патчи ключуются по диапазону ширины (брейкпоинты из конфига) + версии страницы.
- Операции, одинаковые во всех диапазонах, — универсальные, применяются в HTML для всех.
- Операции, различающиеся между диапазонами, на сервере в один HTML не применить (ширина клиента на запросе неизвестна). Варианты: для `style` — переписать в CSS с `@media`; для картинок — собрать `srcset` + `sizes` из замеров разных диапазонов; остальное оставить клиенту.
- Пока не все диапазоны собраны, применяются только универсальные операции.

## Доверие и безопасность

Данные от клиента недоверенные — патч это потенциальный XSS и способ забить кэш.
- Белый список операций: никаких `innerHTML`, `<script>`, `on*`-атрибутов, `javascript:` URL; значения санитизируются.
- Консенсус: принимать патч, только когда N независимых клиентов прислали одинаковый (хэш патча), rate limit на эндпоинт. **Сомнительно, см. ниже.**
- Разрешённые URL для прогрева кэша — только пути внутри uploads и размеры из белого списка/сетки.
- Альтернатива с полным доверием: **автор** запускает пререндер из Svelte UI — страница открывается в iframe'ах нужных ширин прямо в его браузере, патчи записываются и отправляются под авторизацией. Headless на сервере не нужен вообще.

## Сомнения: консенсус (открыто)

Подсчёт совпадающих патчей выглядит ненадёжным:
- **«Независимые клиенты» не проверить.** Один атакующий с пулом IP/прокси набирает N одинаковых патчей; на портфолио с малым трафиком честные N не наберутся вовсе (страница так и не пререндерится).
- **Честные клиенты шлют грязные патчи.** Расширения браузера (переводчики, тёмные темы, Grammarly, блокировщики) тоже мутируют DOM, и `MutationObserver` это видит — отличить мутацию скрипта owo от мутации расширения нельзя. Плюс разные браузеры/версии по-разному отрабатывают feature-detection в скриптах.
- **Совпадение ≠ корректность.** Даже N одинаковых патчей подтверждают только одинаковость, а не то, что это результат именно наших скриптов.

Направления, которые стоит обдумать (ничего не выбрано):
- **Разделить по риску.** Подсказки о ресурсах (`resources`: какие размеры картинок нужны) — низкий риск, их можно принимать от кого угодно с валидацией по пути и сетке размеров: худшее — лишний файл в кэше. DOM-операции — высокий риск (XSS, порча вёрстки), только из доверенных источников.
- **Патч посетителя — не контент, а сигнал.** «Страница X на ширине Y ещё не просчитана / изменилась» → поставить задачу headless-воркеру или показать автору в UI. Тогда клиент экономит не вычисления, а время обнаружения.
- **Доверенный клиент — автор.** Пререндер из Svelte UI в iframe'ах нужных ширин под авторизацией (желательно в профиле без расширений). Один доверенный источник вместо N недоверенных.
- **Статическая проверка операций** против того, что сервер знает сам: добавляемые классы должны существовать в CSS инстанса, URL — внутри uploads, `insert` запрещён вовсе. Сужает урон, но не доказывает корректность.

## Экшен «пререндер всего» в Svelte UI (открыто)

Развитие варианта «доверенный клиент — автор»: в UI кнопка, которая прогоняет все страницы во всех ширинах из конфига прямо в браузере автора.

- SPA открывает каждую страницу в iframe заданной ширины: ширина iframe = viewport для media queries внутри. DPR автора не важен — замеряются CSS-пиксели, а 1x/2x решает `srcset`.
- **Один рекордер, два драйвера.** Тот же скрипт записи патча гоняет и headless-воркер (`Bun.WebView`), и UI автора. Воркер становится опциональным: нет Chromium на сервере — автор жмёт кнопку; есть — работает автоматически.
- SPA должна жить на том же origin, что и страницы (например, `/_owo/ui`), иначе нет доступа к DOM iframe.
- Рекордер подключает сам owo: страница, запрошенная в режиме пререндера (`?prerender` + авторизация), отдаётся с рекордером перед server-скриптами — не нужно ловить момент инъекции из SPA.
- В режиме пререндера owo может не грузить картинки (размеры карточек задаёт грид) — меньше трафика и памяти. Проверить.
- Инкрементально: прогонять только страницы, у которых изменился `source`-хэш; прогресс и возобновление после закрытия вкладки.

Подводные камни:
- iframe с `display: none` не считает layout — нужен видимый (можно за пределами экрана, но с реальными размерами).
- Фоновая вкладка троттлит таймеры и `requestAnimationFrame` — прогон замедлится или зависнет, если автор переключится на другую вкладку.
- Расширения автора внедряются и в iframe'ы — по-прежнему нужен чистый профиль или хотя бы предупреждение в UI.
- Конкурентность ограничить (2–4 iframe), иначе браузер автора захлебнётся на больших инстансах.

## Подводные камни

- Недетерминированные скрипты (random, время, сеть, `localStorage`/тема пользователя) дают разные патчи — консенсус их отсеет, такие скрипты должны быть `client`.
- Персональные данные не должны попадать в патч (то, что зависит от конкретного пользователя).
- Отдавая пререндеренную страницу, сервер помечает её (`data-owo-prerendered="<hash>"`), а клиент пропускает server-скрипты, чтобы не применить изменения дважды.
- Инвалидация — по хэшу исходного HTML + скриптов; при изменении uploads/`.meta/` патчи сбрасываются.

## Порядок источников

Готовый артефакт headless-воркера > принятый клиентский патч > сырая страница + клиентские скрипты (+ запись патча).
