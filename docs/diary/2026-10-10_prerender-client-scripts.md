# 2026-10-10 — пререндер клиентских скриптов `.meta/`: обсуждение

Сессия-обсуждение, кода нет. Исходный вопрос: JS-скрипты инстанса (`.meta/index.js` и импорты) после загрузки меняют вёрстку — переставляют элементы, добавляют классы и inline-стили. Можно ли это делать на сервере и отдавать готовый HTML? Разговор быстро вырос в идею библиотеки shared-скриптов, которой пользователь кастомизирует свою страницу. Всё зафиксировано в трёх заметках в `docs/backlog/`, здесь — только ход рассуждения и где что лежит.

## Как менялось решение

- Сначала разобрали скрипты в `test/uploads/.meta/`: статичные мутации (хак xtc-toaster в `common.script.js`), подбор размера картинок по `getBoundingClientRect` (там же) и интерактив (`frames.script.js`). Интерактив — только клиент, это не обсуждается.
- Первая идея — декларативные правила в Go через goquery — отпала: пользователь хочет унификацию «всё на JS» и два типа скриптов, `client` и `server` (prerender).
- Затем — goja + esbuild + свой DOM-шим в Go, а ширину карточек вычислять из класса `card--span-N` по фиксированным колонкам грида. Отпало: грид у каждого инстанса свой (CSS инстанса), ширину надо измерять, а без layout-движка нечем.
- Скрипт с картинками оказался главным кандидатом на сервер, а не на клиент: картинки должны быть нарезаны заранее. Сейчас ресайз ленивый (`GetResizedImagePath`, семафор на 3), первый посетитель ждёт.
- Headless-браузер: один снапшот = один viewport, поэтому браузер — не «финальный DOM», а измеритель: прогнать страницу на нескольких ширинах → `srcset` + `sizes` в одну страницу + прогрев кэша. Рендер «на запросе под ширину клиента» отвергли: ширина на первом запросе неизвестна (Client Hints только в Chromium и не сразу), задержка, ломается при ресайзе.
- `Bun.WebView` существует (экспериментальный), но на Linux гоняет установленный Chrome по CDP — Chromium в образе нужен всё равно. WebKit не легче.
- Пользователь задал архитектуру: Bun-сервис пререндера через очередь, API на Bun, Go остаётся сборщиком страниц, Svelte SPA для библиотеки скриптов; всё опционально и конфигурируется yaml/json/cli.
- Самое интересное направление — пререндер силами клиентов: браузер посетителя выполняет скрипты, `MutationObserver` фиксирует затронутые узлы, финальное состояние уходит на сервер JSON-патчем, Go применяет его к своему HTML. Универсально для любых DOM-мутаций, не только замеров.
- Доверие к патчам от посетителей — главная дыра: консенсус N совпадений ненадёжен (Sybil, малый трафик, расширения браузера мутируют DOM). Сдвинулись к «доверенный клиент — автор»: экшен в Svelte UI прогоняет все страницы во всех ширинах в iframe'ах в браузере автора. Один рекордер — два драйвера (headless-воркер и UI автора).

## Что осталось открытым

- Доверие к патчам: принимать ли что-то от посетителей вообще (разделение по риску: подсказки о ресурсах — от всех, DOM-операции — только автор/воркер), или патч посетителя — только сигнал «страница не просчитана»
- Как помечать тип скрипта (`*.server.js` / `export const target` / раздельные точки входа)
- Как server-скрипт отдаёт замеры по нескольким ширинам и как они склеиваются в `sizes`
- Какая очередь (Redis+BullMQ / NATS / SQLite) и где хранить конфиг скриптов страниц (`.meta/` или БД API)
- Авторизация API/UI — у owo её нет совсем
- Проверить на практике: можно ли в режиме пререндера не грузить картинки (размеры карточек задаёт грид), реальные цифры нагрузки `chrome-headless-shell`
